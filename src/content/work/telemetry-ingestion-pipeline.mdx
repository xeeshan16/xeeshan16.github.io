## Context

The pipeline ingested telemetry from distributed sources and passed it downstream for processing. Traffic grew to four times its starting volume, and the system had to keep up without dropping data, double-counting it, or needing someone to resize it by hand.

## Approach

- Go processors consuming from Kafka, running on Kubernetes.
- Redis for the fast shared state the processors needed between steps.
- Checkpointed processing, so a restarted processor resumes from where it stopped instead of from the beginning.
- Dead-letter queues for messages that can't be processed, so one bad record doesn't block a partition.
- Autoscaling on Kafka consumer lag rather than CPU.

## Key decisions

**Idempotent processors, not exactly-once hopes.** Kafka redelivers after failures and rebalances. Each processor was made idempotent, so a message seen twice has the same effect as one seen once, which made retries and restarts safe by design.

**Scale on the signal that matters.** CPU says little about whether a consumer is falling behind; consumer lag says exactly that. Scaling on lag added capacity when backlogs built up and released it when they drained.

**Isolate poison messages.** Sending unprocessable records to a dead-letter queue kept the main flow moving and left the failures somewhere they could be inspected and replayed.

## Production story

### Keeping up while traffic grew fourfold

**What happened.** As traffic grew, a fixed-size consumer fleet risked falling behind at peaks. Growth also made failure modes more frequent: every restart or rebalance could replay messages that had already been processed, and a single record that couldn't be processed could stall its whole partition.

**The fix.** Each failure mode got its own answer:

- **Scale on consumer lag, not CPU.** Lag measures directly whether consumers are keeping up, so the autoscaler added processors when backlogs built and removed them when they drained.
- **Idempotent, checkpointed processors.** Adding processors triggers rebalances, and rebalances replay messages. Because every processor checkpoints its progress and is idempotent, a replayed message has no extra effect.
- **Dead-letter queues.** A record that can't be processed is parked for inspection and replay, and the partition keeps moving.
