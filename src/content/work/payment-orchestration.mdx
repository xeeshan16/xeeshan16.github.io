## Context

The platform moves card and wallet payments between customer channels, partner networks and the bank's core systems, and it feeds anti-fraud and transaction-risk workflows along the way. In payments a bug rarely shows up as an error. It shows up later as a customer charged twice or a ledger that doesn't balance.

## Approach

- Java 17/21, Kotlin and Spring Boot 3 services, using Java concurrency (the Executor framework, CompletableFuture) and explicit transaction boundaries on PostgreSQL and Oracle.
- A Kafka- and SQS-driven architecture: Kafka for payment events between services, SQS where a buffered work queue fit better, and idempotent consumers throughout.
- Secure REST APIs with OAuth2 and Spring Security, plus mutual TLS.
- Containerised services deployed to Azure AKS through CI/CD, with Kubernetes probes and PodDisruptionBudgets so rollouts and node maintenance don't drop traffic.
- Distributed, time-ordered transaction IDs generated with the Snowflake algorithm, so no service has to ask a central sequence.

## Key decisions

**Isolate slow dependencies instead of scaling into them.** When downstream services slowed, the obvious responses were to scale out consumers or add aggressive retries. I rejected both: they would have sent even more load to dependencies that were already struggling. Instead we used a Kafka and SQS architecture with back-pressure and circuit breakers, so a slow service is isolated without blocking payments.

**Prove fraud and risk changes on real traffic first.** Before a change to fraud or risk logic goes fully live, a controlled subset of production traffic is routed to services hardened with Resilience4j, and we compare latency, error rates and false-positive and false-negative rates against the existing flow.

**Reconcile everything.** I built reconciliation for card settlement files, wallet balances and mismatches between partner records and core banking, so discrepancies are caught by the system rather than by a customer.

**Test the contracts between services.** Alongside unit tests with JUnit 5 and Mockito and integration tests on real databases with Testcontainers, Pact contract tests catch a breaking API change before it ships.

## Production stories

### Duplicate payments from Kafka redeliveries

**What happened.** Kafka delivers at least once. After a consumer restart or a partition rebalance, messages that had already been processed were delivered again, and some payments were processed twice.

**The fix.** The rule is simple: a redelivered message must never initiate a second payment. Each transaction is identified by a stable payment (idempotency) key, and the consumer checks its persisted state before doing anything. State transitions are atomic, so two consumers can't claim the same payment at the same time. A redelivery of a payment that already succeeded is acknowledged and skipped.

**When the outcome is unknown.** The hard case is a crash or timeout after the payment was sent but before its result was recorded. That payment isn't safe to skip and isn't safe to resend. Instead of blindly resubmitting, the consumer marks it PENDING (or UNKNOWN) and verifies the outcome with the authoritative payment or orchestration system. Transient failures get bounded retries; payments that stay unresolved or go stale move into reconciliation, with monitoring and alerting so someone sees them.

### Deadlocks on concurrent wallet balance updates

**What happened.** Concurrent updates to wallet balances deadlocked in PostgreSQL and Oracle: two transactions each held a lock the other needed, and the database had to abort one of them.

**The fix.** Two changes. Shorter transactions, so locks are held for less time and contention windows shrink. And a consistent lock order, so any two transactions that touch the same rows acquire their locks in the same sequence and can never wait on each other in a cycle.

### Latency spikes from GC pressure under load

**What happened.** Under load, garbage-collection pauses on the Java payment services showed up as latency spikes.

**The fix.** Four changes, each aimed at either allocating less or collecting more predictably:

- Tuned the garbage collector and its settings.
- Optimised the services' thread pools.
- Removed orphaned objects that were retaining memory.
- Switched Spring beans from prototype to singleton scope where they held no per-use state, cutting allocation churn.

## What I'd do differently

I'd build automated reconciliation and stale-pending detection earlier, rather than after the core flow was live. Backed by the idempotency guarantees and by replay testing — deliberately re-running retries, duplicate deliveries and ambiguous outcomes against the system — they turn payment correctness from something we reasoned about into something we continuously prove.

## Outcome

Fault-tolerant processing for more than 100,000 card and payment transactions, measured by guaranteed delivery and idempotent handling of retries, underpinning the bank's credit card, wallet and anti-fraud products. Payment flows stay stable when downstream services slow down. I lead the six engineers who build and run it.
